# Offline evaluation results — 2026-09-21

## Verdict

**Forecasting helps. The neural network does not.**

Two separate findings, and they point in opposite directions:

1. **Scaling from a forecast beats scaling reactively.** Replaying the operator's own rules,
   any forecaster cut the number of ten-minute intervals where capacity was short from **12
   to 3–5**, for about **1.4% more replica-minutes**. The project's premise is sound.
2. **The LSTM is the worst forecaster tested, and is unstable.** It lost to a one-line
   previous-day baseline in **10 of 10 runs**, and in **4 of 10** its output diverged by one
   to eleven orders of magnitude. The preregistered bar — 10% lower MAE than the strongest
   baseline — was not approached in any run, in any scenario, at any horizon step.

The honest conclusion for this workload: **the network is unnecessary.** The seasonal
pattern component alone is the best forecaster measured, and it is roughly fifty lines of
arithmetic. Matching a simpler baseline means the network is not earning its place *here*;
it does not mean predictive autoscaling cannot work, and the operational numbers show it
does.

## How this was produced

Repository code, not a reimplementation: the same `LSTMForecastModel`, the same blend, the
same operator decision rule. Rolling origins, information availability identical at each
origin, retraining on the six-hour CronJob schedule with a twenty-minute publication delay,
400 origins per run (about 2.8 days), twelve-day synthetic series, multiple seeds.

Reproduce:

```sh
eval/.venv/bin/python eval/offline_eval.py --full --out eval/results.json
eval/.venv/bin/python eval/offline_eval.py --failure-modes
```

Raw output: `eval/results.json`, `eval/failure-modes.json`.
Data provenance: synthetic series generated by `make_series()` with stated seeds; the real
series in `eval/data/benchmark-nginx-test.json` is a read-only Prometheus export from the
benchmark cluster.

the seasonal pattern carries a consistent **+43 bias**: it over-predicts by design, because
it takes the 75th percentile of recent days. For an autoscaler that bias is deliberate and
useful; for a forecaster it is a systematic error worth stating.

## Operational replay — what it means for capacity

Repeating scenario, seed 1, 1262.9 RPM per replica, replicas bounded 1–12, two-minute
readiness delay.

| Predictor | replica-minutes | scaling events | intervals short | minutes short | max shortfall |
|---|---|---|---|---|---|
| served blend | 13640 | 20 | 3 | 30 | 1 |
| network only | 13950 | 20 | 5 | 50 | 1 |
| seasonal pattern | 13690 | 22 | 4 | 40 | 1 |
| previous day | 13680 | 22 | 4 | 40 | 1 |
| trend adaptive | 13690 | 22 | 4 | 40 | 1 |
| **reactive only** | **13450** | **22** | **12** | **120** | **1** |

Forecasting of any kind removes about two thirds of the shortfall intervals for roughly 1.4%
more replica-minutes. The differences *between* forecasters are one interval wide — well
inside the noise of a single run — so this table supports "forecast beats react" and does
not support any ranking among the forecasters.

## Training instability

In four runs the network's output diverged:

| Run | network MAE | previous-day MAE |
|---|---|---|
| repeating seed 2 | 6.1×10³ | 135.9 |
| level shift seed 2 | 3.4×10¹³ | 135.9 |
| spike seed 1 | 1.9×10³ | 142.7 |
| weekly seed 1 | 7.9×10⁴ | 142.4 |

Same architecture, same hyper-parameters, different seed or scenario. The likely cause is
the `relu` activation inside the LSTM layers (`lstm_model.py`), which permits unbounded
activations; the default `tanh` does not. This was not changed here — an architecture change
needs its own review and its own evidence — but it is recorded as the first thing to try if
the network is kept.

The blend limits the damage but cannot contain it: with the network at 10¹³ the blended
output is still dominated by it, because the blend is a weighted average, not a clamp. If
the network is kept, the served forecast needs a sanity clamp against the seasonal pattern.

## Failure modes

All handled (`eval/failure-modes.json`):

| Condition | Behaviour |
|---|---|
| Cold start, less than one window | Refused cleanly: "Insufficient data: 72 points (need 150)" |
| All-zero series | Finite output, no crash |
| Gap in the seasonal history | Pattern still sourced from real history; no invented values |
| Delayed observation (40 min stale) | Forecast anchored to the data's clock, not the wall clock |
| Level shift / spike | Recovers; previous-day recovers faster |
| Old-format artifact | Detected and refused |
| Retrain landing mid-peak | No failures |

## What this evaluation cannot show

- **Latency.** Replay models capacity arriving after a readiness delay. It does not model
  queueing, connection behaviour or response time. No latency claim is supported by anything
  here.
- **Generalisation from real traffic.** The benchmark cluster had 248 ten-minute points when
  this ran — below the 288 needed for a two-day warm-up plus rolling origins — so the real
  series could not be scored at all. Every number above is from synthetic series. That is a
  limit on external validity, not a formality.
- **A ranking among forecasters operationally.** One interval of difference across a single
  run is not a result.

## What to do with this

1. Keep the predictive layer. It does what it was built to do: capacity arrives before the
   demand, and the shortfall drops by two thirds.
2. Make the seasonal pattern the default forecaster. It is the best performer measured, it
   is stable, and it is far simpler.
3. Treat the network as an experiment that has not paid off on this workload. Before keeping
   it: switch the LSTM activation off `relu`, clamp the served forecast against the pattern,
   and re-run this harness. If it still cannot beat previous-day by 10%, remove it.
4. Re-run against real traffic once the benchmark has several days of history. Synthetic
   repeating traffic is the easiest possible case for a seasonal baseline and the least
   informative case for a learned model.
